# Technical Evidence Register — Project 01

This document records the external evidence behind the Project 01 specification. Other
documents cite entries by ID (for example `EV-04`). Research was performed on
**2026-11-04**. Sources change over time, so re-check an entry before relying on it for a
new decision.

## 1. Claim types

Every statement in the specification falls into one of these categories. Documents label
non-obvious statements with the tag in brackets.

| Tag | Meaning |
| --- | ------- |
| `[DOC]` | Officially documented behaviour of an external system, with a source in this register. |
| `[OBS]` | Directly observed on a real machine during research (recorded below with date and machine). |
| `[DES]` | Our design decision. Justified by evidence but not itself a fact about external systems. |
| `[ASM]` | Implementation assumption. Plausible and partly supported, but **must be verified** during implementation or hardware validation. |
| `[FUT]` | Future feature proposal. Not in V1 scope. |

## 2. Source register

| EV-01 | [NVIDIA SMI documentation](https://docs.nvidia.com/deploy/nvidia-smi/index.html) | `nvidia-smi` is built on NVML. Its output "is not guaranteed to be backwards compatible", while "NVML and the Python bindings are backwards compatible, and should be the first choice when writing any tools that must be maintained across NVIDIA driver releases". | DEC-04: NVML is the primary source; `nvidia-smi` is detection plus fallback only. |
| EV-02 | [NVIDIA SMI documentation — selective queries](https://docs.nvidia.com/deploy/nvidia-smi/index.html) | `--query-gpu=<fields> --format=csv[,noheader][,nounits]` is the documented scripted query interface; `csv` is mandatory. | Fallback adapter query format (architecture §4.5). |
| EV-03 | [NVIDIA SMI documentation — `-q` fields](https://docs.nvidia.com/deploy/nvidia-smi/index.html) | "Driver Version" is deprecated in favour of "KMD Version". "CUDA Version" is deprecated in favour of "CUDA UMD Version", described as "the latest CUDA version supported by the driver. This is usually, but not always, the version of the CUDA toolkit installed on the system." | D03 wording; the field is named `driver_supported_cuda_version` and never `cuda_version` or `toolkit_version`. The parser must accept both old and new labels. |
| EV-04 | [NVML API — System Queries](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlSystemQueries.html) | `nvmlSystemGetCudaDriverVersion` returns the CUDA driver version and, "if the cuda library is not found", returns "a known supported version number". `nvmlSystemGetCudaDriverVersion_v2` calls `cuDriverGetVersion()` and returns `NVML_ERROR_LIBRARY_NOT_FOUND` if `libcuda.so.1`/`libcuda.dll` is missing. Major = `v/1000`, minor = `(v%1000)/10`. `nvmlSystemGetDriverVersion`, `nvmlSystemGetNVMLVersion` exist. | Driver collector methods; `cuda_driver_library` evidence in D01. |
| EV-05 | [NVIDIA CUDA Compatibility guide](https://docs.nvidia.com/deploy/cuda-compatibility/index.html) | Minor Version Compatibility (from CUDA 11) lets applications built within the same major CUDA release run on a sufficiently new driver, with some feature limitations. Forward Compatibility uses a `cuda-compat` package to run newer toolkits on older drivers across major versions, subject to platform and GPU support. | D01/D03 rules compare CUDA **major** versions only; same-major differences are never reported as a root cause. Forward compatibility is listed as a limitation of every version-based inference. |
| EV-06 | [NVML API — Device Queries](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html) | `nvmlDeviceGetMemoryInfo` reports used/free/total bytes. The reserved amount is v2 only. "Under WDDM most device memory is allocated and managed on startup by Windows". In MIG mode the aggregate needs privileges. Some iGPU SoCs return `NVML_ERROR_NOT_SUPPORTED`. `nvmlDeviceGetMemoryInfo_v2` includes reserved memory in used. `nvmlDeviceGetTemperature` is deprecated in favour of `nvmlDeviceGetTemperatureV`. `nvmlDeviceGetTemperatureThreshold`, `nvmlDeviceGetPowerUsage` (milliwatts), `nvmlDeviceGetCudaComputeCapability`, `nvmlDeviceGetUUID`, `nvmlDeviceGetPciInfo_v3`, `nvmlDeviceGetComputeRunningProcesses_v3`, `nvmlDeviceGetGraphicsRunningProcesses_v3` exist. | Hardware and runtime collector methods; units; MIG and WDDM limitations; "used ≠ total − free" rule. |
| EV-07 | [NVML API — `nvmlUtilization_t`](https://docs.nvidia.com/deploy/nvml-api/615/api/structnvmlUtilization__t.html) (the unversioned `structnvmlUtilization__t.html` URL returned HTTP 404 during research; the versioned page and search index were used) | `gpu`: percent of time one or more kernels was executing. `memory`: percent of time global (device) memory was being read or written. Sample period between 1 s and 1/6 s depending on product. | Field is named `memory_bus_utilization_percent`, never "memory used %". Snapshot limitation text. |
| EV-08 | [NVML API — `nvmlProcessInfo_t`](https://docs.nvidia.com/deploy/nvml-api/latest/api/structnvmlProcessInfo__t.html) | `usedGpuMemory`: "Under WDDM, NVML_VALUE_NOT_AVAILABLE is always reported because Windows KMD manages all the memory and not the NVIDIA driver." | Per-process memory is `NOT_SUPPORTED` on Windows WDDM (AC37). |
| EV-09 | [CUDA on WSL User Guide](https://docs.nvidia.com/cuda/wsl-user-guide/index.html) | The Windows driver is stubbed into WSL2 as `libcuda.so`, and a Linux NVIDIA driver must not be installed inside WSL2. `nvidia-smi` lives at `/usr/lib/wsl/lib/nvidia-smi`. "NVML (nvidia-smi) does not support all the queries yet": GPU utilization and active compute processes are not yet supported. | WSL2 platform profile; D06 expected `NOT_SUPPORTED` metrics; `nvidia-smi` search path; D01 recommendations never suggest installing a Linux driver inside WSL2. |
| EV-10 | [CUDA Programming Guide — Environment Variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html) | `CUDA_VISIBLE_DEVICES`: unset means all devices are visible and an empty string means none. It accepts `nvidia-smi` indices, UUIDs or MIG IDs, and an invalid index truncates the list. `CUDA_DEVICE_ORDER`: `FASTEST_FIRST` (default, heuristic) or `PCI_BUS_ID`. | D08; NVML↔PyTorch device correlation by UUID/PCI rather than index (DEC-09). |
| EV-11 | [`nvidia-ml-py` on PyPI](https://pypi.org/project/nvidia-ml-py/) | NVIDIA's Python bindings for NVML (BSD licence, import name `pynvml`, pure `ctypes` wrapper). NVML return codes are raised as exceptions such as `NVMLError_LibraryNotFound`, and `NVML_VALUE_NOT_AVAILABLE` is mapped to `None`. Latest version at research time: 13.615.71. | DEC-05 (dependency choice); error-to-status mapping (data model §3.3). |
| EV-12 | [PyTorch `torch.cuda` API](https://docs.pytorch.org/docs/stable/cuda.html) and [`torch/cuda/memory.py` source](https://github.com/pytorch/pytorch/blob/main/torch/cuda/memory.py) | `torch.cuda` is lazily initialised; `is_available()`, `is_initialized()`, `device_count()`, `get_device_properties()`, `get_device_capability()` exist. `mem_get_info()` returns global free/total via `cudaMemGetInfo`. `memory_allocated()` = memory occupied by tensors; `memory_reserved()` = memory managed by the caching allocator. **Source:** `memory_stats_as_nested_dict()` returns `{}` when `not is_initialized()`, so `memory_allocated()` then returns `0`. | DEC-08 (allocator stats `NOT_APPLICABLE` unless CUDA is initialised in the calling process); AC16. |
| EV-13 | [PyTorch CUDA semantics](https://docs.pytorch.org/docs/stable/notes/cuda.html) and [PyTorch CUDA environment variables](https://docs.pytorch.org/docs/stable/cuda_environment_variables.html) | The caching allocator's unused memory "will still show as if used in `nvidia-smi`". `CUDA_VISIBLE_DEVICES` controls which GPUs PyTorch sees. `PYTORCH_NVML_BASED_CUDA_CHECK=1` makes `is_available()` use NVML instead of the CUDA runtime. `PYTORCH_ALLOC_CONF` (alias `PYTORCH_CUDA_ALLOC_CONF`) configures the allocator. | Separation of device-wide and allocator memory (AC05); environment variable allowlist. |
| EV-14 | [`torch.cuda.get_device_properties`](https://docs.pytorch.org/docs/stable/generated/torch.cuda.get_device_properties.html) and [pytorch/pytorch#151672](https://github.com/pytorch/pytorch/pull/151672) | Returns `_CudaDeviceProperties`. ## 4. Key claims and their classification

| # | Claim | Type | Evidence |
| - | ----- | ---- | -------- |
| C01 | The `nvidia-smi` header "CUDA Version" / "CUDA UMD Version" is the newest CUDA version the driver supports, not the installed toolkit. | `[DOC]` | EV-03, EV-04 |
| C02 | The NVML CUDA driver version may be a "known supported version" when `libcuda` is missing. | `[DOC]` | EV-04 |
| C03 | Same-major CUDA differences between a framework build and the driver aren't a reliable failure signal because of minor version compatibility. | `[DOC]` + `[DES]` | EV-05 |
| C04 | NVML memory utilization % is memory-bus activity, not memory occupancy. | `[DOC]` | EV-07 |
| C05 | NVML `used` may not equal `total − free` (reserved memory is part of used in v2). | `[DOC]` | EV-06 |
| C06 | Per-process GPU memory isn't available under Windows WDDM. | `[DOC]` | EV-08 |
| C07 | GPU utilization and active-process queries aren't supported in WSL2. | `[DOC]` | EV-09 |
| C08 | PyTorch allocator stats are `0` when CUDA isn't initialised in the calling process. | `[DOC]` (source code) | EV-12 |
| C09 | CUDA and NVML device indices may differ. | `[DOC]` | EV-10, EV-17 |
| C10 | Calling `torch.cuda.mem_get_info()` creates a CUDA context on the device, which itself uses device memory. | `[ASM]` | Follows from `cudaMemGetInfo` needing a context; not stated verbatim in the PyTorch docs above. Verify in HW-04. |
| C11 | PyTorch's `get_device_properties()` doesn't significantly change NVML-reported free memory when run in a short-lived subprocess after the NVML snapshot. | `[ASM]` | Verify in HW-04. |
| C12 | `version.json` reliably identifies CUDA 11.1+ toolkits. | `[ASM]` | EV-20 (community only). Verify in HW-05. |
| C13 | Importing `pynvml` from `nvidia-ml-py` doesn't load the NVML shared library until `nvmlInit()`. | `[ASM]` | Consistent with EV-11 (`ctypes` wrapper) but not stated explicitly. Verify by unit test on a machine without NVML. |
| C14 | A driver-independent PCI scan can detect an NVIDIA GPU whose driver isn't loaded (bare-metal Linux). | `[ASM]` | EV-26. Verify in HW-02. |
| C15 | A single temperature sample can't establish thermal throttling. | `[DES]` | Sampling is instantaneous; throttling is a sustained clock behaviour (see D07). |
